# Known gaps between the code and the table
{: .no_toc }

The [Lifecycle Table]({{ '/state-machine/table/' | relative_url }}) is the source of truth. The places below are where the code does not yet do what the table says, or where `lifecycle check` does not yet catch a violation. Each entry names the table rows involved and the behavior the table requires. Remove an entry in the change that fixes it.

## A repository renamed during upstream review is not followed

- **Where:** `upstream_review.*`; `require_renamed_upstream`, and `resume_upstream_revision` and `resume_upstream_read` in `upstream_review.waiting_human`; the collector (`collect.upstream_snapshots`).
- **Today:** when the upstream repository is renamed or transferred while the upstream PR is open, GitHub keeps the PR and answers the recorded repository id under the new name. The collector reports the new name, and once revision Work is due in `upstream_review.fix_needed` the controller takes `require_renamed_upstream` at once. The record keeps `upstream.full_name`, which also names the contribution id, its project, and the intake dedupe, so no row rebinds it: the only route is park, abandon, and a new request for the new name, which opens a second upstream PR for the same change.
- **Table:** `require_renamed_upstream` leads to the human wait with `upstream_unavailable` and no counter, and `resume_upstream_read` leaves it only once the repository is read under its recorded name again; a resume before then waits again at once.
- **Required:** a table decision to follow a repository rename while the upstream PR is open, verified by `upstream.repository_id` equality (for example rebind `upstream.full_name` and the PR URL, keeping the contribution id and project under the old name).

## Release acceptance has no recorded contract

- **Where:** `release_wait.idle`; `release.acceptance_contract` and the release observation in `observe_ci.py`.
- **Today:** the acceptance contract is read from the target contract the record names (`target_contract_id`, its `distributions` and `release_rows`), but nothing records a target contract, so every contribution that reaches `release_wait.idle` takes `require_release_intervention` with the pending action `release_contract_missing`. Its resume (`resume_release_observation`) returns to `release_wait.idle`, which asks again at the next observation. The wait has reminders; `park` does not apply in `release_wait.*`, so the contribution stays there until a contract exists.
- **Table:** `verify_release` requires verified release coverage that satisfies the acceptance contract; `release_wait.*` has no other exit.
- **Required:** a producer of the frozen release matrix (the target contract's distributions and rows) before a contribution reaches `release_wait`, and a table decision on how a contribution leaves `release_wait` when the release can never be verified.

## Release verification does not run the install probe

- **Where:** `verify_release` in the release observation; `probe.py`.
- **Today:** release coverage is verified from the official PyPI metadata (non-yanked wheels with a digest, uploaded after the merge, whose tags cover every row) and the provenance of the release tag (it contains the merge commit). The wheels are not downloaded, inspected, installed, or imported; the evidence record says so in its limitations.
- **Table:** `verify_release` requires "verified release coverage satisfies the acceptance contract".
- **Required:** a decision on whether release acceptance requires the install-and-import probe in a clean target environment, then a trusted probe run before `verify_release`.

## Release coverage is read from PyPI only

- **Where:** `release_wait.idle` (`verify_release`, `require_release_intervention`, `record_release_incomplete`); `release.py`.
- **Today:** planning and development serve projects of any language, but the release observation reads release coverage from PyPI only. A contribution whose project releases through another channel (crates.io, npm, Go modules, Maven, container images, GitHub releases, distribution packages) can never have its release verified from that channel, so it waits in `release_wait.waiting_human` for an operator, like a contribution without a recorded contract.
- **Table:** `verify_release` requires verified release coverage that satisfies the acceptance contract, whatever channel the project releases through.
- **Required:** a trusted reader of the release channels the plan records in `project.release_channels`, and the acceptance contract for them.

## Provisioning and development PR operations validate the checked-out state only

- **Where:** `provision.yml` (`python -m provisioning`) and `dev-pr.yml` (`python -m dev_pr`, and `python -m ci_rerun operation` in development).
- **Today:** each job checks out the commit the run was dispatched at and validates the operation against that checkout only; it does not check that the checkout is the head of `main`, and it does not read the head of `main` again before its write. A pause, a `read_only` policy, or a closed operation committed to `main` after the dispatch is not seen, so the write can still run once. The handoff workflow has both checks (`handoff.current_state` before the token, `handoff.unchanged_on_main` before each write).
- **Table:** `pause` stops new Work and writer admission; the operations run only while the policy permits the write and the operation is the record's current planned intent.
- **Required:** the same checks as the handoff workflow (the checkout is the head of `main` before the token, and the state of the operation is unchanged at the head of `main` immediately before each write), or a decision that the window is acceptable.

## The planner and worker agents run on the runner, outside the sandbox

- **Where:** `planner.md` and `worker.md` (`sandbox.agent: false`, `features.dangerously-disable-sandbox-agent: true`, `strict: false`, `tools.bash: ["*"]`); their `agent` jobs; the steps after the agent in those jobs.
- **Today:** no AWF sandbox or firewall runs for these agents. They run as the runner's user on the runner itself with a full shell, so `network.allowed` is not enforced (any host is reachable, and anything read can be sent anywhere), and the runner's user has passwordless sudo on the GitHub-hosted runner and is in the `docker` group, so it can become root directly with `sudo` or through Docker. Every step after the agent in the same job runs code the agent could have replaced: gh-aw's own steps load their scripts from `${RUNNER_TEMP}/gh-aw/actions`, `run:` steps find `bash` and every command on the runner's PATH, and "Configure Git credentials" runs git in the workspace. Those steps hold `ANTHROPIC_API_KEY`, `GH_AW_GITHUB_MCP_SERVER_TOKEN`, `GH_AW_GITHUB_TOKEN` and the job's `GITHUB_TOKEN` ("Redact secrets in logs", the rate-limit and git credential steps), and, as actions, the run's artifact token, so the agent can take them, and through Docker it can also read the provider key the Pi provider patch keeps in the Pi process and the gateway's GitHub token. The job's `GITHUB_TOKEN` is read-only (`actions`, `contents`, `issues`, `pull-requests`). The agent can also write the agent artifacts in any form. What holds is the job boundary, and only while `GH_AW_GITHUB_TOKEN` and `GH_AW_GITHUB_MCP_SERVER_TOKEN` are unset or read-only: the `safe_outputs`, `record`, `notify` and `publish` jobs run on fresh runners, check the native Result, the plan gate or the worker gate and the trusted state again, and only they hold write tokens. The repository expects both unset, so that gh-aw falls back to the job's read-only `GITHUB_TOKEN`: `.github/repository-settings.json` declares no repository secrets and only `ANTHROPIC_API_KEY`, `RISEPROJECT_APP_PRIVATE_KEY` and `RISEPROJECT_UPSTREAMING_APP_PRIVATE_KEY` among the organization secrets selected for it, and the owner confirmed on 2026-11-24 that no `GH_AW_*` secret is set at the organization level, so the job boundary holds as declared in the repository settings and confirmed by the owner for the organization; a live audit verifies it. `scripts/audit_repository_settings.py` compares a settings snapshot with that declaration and fails on any `GH_AW_*` secret in either, and `--live OWNER/REPO` reads the names of the repository's own secrets, the organization secrets visible to it and its environment secrets from GitHub and fails on any `GH_AW_*` name; CI runs the audit only on the committed fixture, so a secret added on GitHub is caught only by a live audit. A write token stored under either name, at the repository, organization or environment level, would be readable by these agents and would break the boundary. The dispatcher and the reviewer are the only workflows whose agents are sandboxed, and the dispatcher is the only agent without a shell or file writes (the reviewer's shell is covered by its own entry below); the home directories their sandbox mounts read-write are owned by root before they run (`~/.local/bin`, where their rootless AWF is installed first on PATH, among them; the planner and worker install no AWF).
- **Review children:** the reviewers and the fix worker of the worker's review loop are foreground `pi-subagents` sessions inside the worker's Pi process, so they run on the runner with it. Their tools are read, grep, find and ls (the fix worker has bash, edit and write), they hold no destination credential, and they inherit the worker's provider and credential-free environment.
- **Table:** not a row of the table; the trust boundary the workflows rely on for every effect.
- **Decision:** accepted by the owner on 2026-11-24: "Keep running planner and worker outside of the sandbox." The risk above stands, and the job boundary holds only while no `GH_AW_*` secret reaches the repository; the owner confirmed none is set at the organization level, and a live audit (`scripts/audit_repository_settings.py --live`) checks it. Should the decision be revisited, with gh-aw v1.2.2 and AWF v0.29.11: the planner needs `sandbox.agent` on (the Docker runtime) and `strict: true`, a `network.allowed` list that covers its web research (the `pi-web-access` extension, which the planner and the worker both have, reaches arbitrary sites, so that is a real restriction), native threat detection becomes available, and the same pre-agent step as the dispatcher (the home directories AWF mounts read-write owned by root, since a sandboxed shell can still write them) plus checks after the agent that run no PATH command and load no code from the workspace. The worker also needs host Docker and QEMU, which the Docker runtime does not give the sandbox: `sandbox.agent.args: ["--enable-dind"]` passes the host Docker socket in, which is root on the runner and bypasses the firewall through new containers, so it contains nothing; `runtime: docker-sudo-iptables` runs AWF privileged with host access; the `cloud-hypervisor` and `nvx` microVM runtimes need KVM on the runner and a Docker and QEMU inside the guest. An upstream fix would let gh-aw run the worker's builds through a trusted Docker proxy outside the sandbox, mount the home tool directories read-only (or not at all) unless a workflow asks for them, and install the rootless AWF outside any directory it mounts.

## Workflow commands in the agent step's output are not suspended

- **Where:** `worker.md` ("Suspend workflow commands around untrusted agent output" and its post-step); the "Execute Pi CLI" step of every agent job.
- **Today:** the Actions runner scopes `::stop-commands::` to the step that writes it (each step's handler creates its own `ActionCommandManager`), so the worker's pair suspends commands only in its own pre-agent step and post-step, not in the agent step between them. A line of the agent's output that starts with `::` can still issue a workflow command in the agent step: an annotation, a mask, a log group, a problem matcher, or an output of that step, which no job reads; the runner keeps `set-env` and `add-path` disabled. gh-aw's later steps that print agent logs suspend commands within themselves.
- **Table:** not a row of the table.
- **Required:** suspend workflow commands inside the agent step itself (around Pi's output), which gh-aw v1.2.2 does not offer, and remove the worker's pair, which protects nothing.

## An accepted Result whose report cannot be stored pauses the contribution

- **Where:** `worker_report.evidence`, `reconcile.report_evidence` in the folds of the six rows of `reconcile.REPORT_VERBS`, and `reconcile.pushed_report_evidence` in the folds of a Result whose push may have landed (an `uncertain` Result held for a publish-only retry, a retry rejected as stale behind the operation of an earlier attempt).
- **Today:** a success Result of Work that carries a history always has a report the gate accepted. When the reconciler finds that report missing, unreadable or invalid in the publication artifact, or cannot build its evidence, it raises `worker_report.ReportError` inside the contribution's isolation block: the tick takes `pause_on_processing_error` instead of the success row, with a reason that names the Work. The pause is specific to that contribution (`isolation.ContributionPause`) and any number of them in one tick stop nothing else. The pause clears the Work, so that Result takes `record_late_effect` the next tick, whose event records that its report could not be stored, and the artifact is not acted on again; a publication it made is seen only by head observation after the resume. The report itself cannot be recovered from that artifact.
- **Table:** the six rows store the report of the Work as `worker_report` evidence; no row folds a success Result without its report.
- **Required:** a table decision on an accepted Result whose report is lost after the gate (for example a row that folds it with a recorded loss, or a retry of the publication artifact).

## A publication job lost after its push leaves no report

- **Where:** the publication job of `worker.md` and `publish-retry.yml`, and `reconcile.fold_patch_result`.
- **Today:** the report of a Result whose push may have landed is stored when the Result is folded, whatever ends the hold afterwards. A publication job whose runner is lost after its push and before it uploads the publication artifact, which it uploads even after a failed step, leaves no Result: dispatch recovery or the wait for a publish-only retry ends the Work, the branch observation can confirm the push, and CI runs on that head, but no report of that Work is ever read, so a repair after failing CI on it reads the CI without the report of the worker that left the head.
- **Table:** a held publication ends by a retry Result, the exhaustion of `publish_recovery`, or a stop; no row reads a report from anywhere but a folded Result.
- **Required:** the report uploaded before the push (for example in a separate artifact the reconciler reads when the branch observation confirms an operation whose Result never arrived).

## A failure of the pipeline after the agent is charged to the Work

- **Where:** `pipeline_failure.classify`, `reconcile.dispatch_recovery`, and the jobs after the agent of `worker.md` and `planner.md` (`safe_outputs`, `publish`, `continuation`).
- **Today:** only a run that failed before its agent ran (`Execute Pi CLI` skipped), in a step that does not depend on the contribution, or in its `activation` job, is held and later reallocated without a charge (`reallocate_after_pipeline_failure`). A run whose agent ran and whose later job failed for the pipeline (a failed `safe_outputs`, a gateway that stopped, an artifact that was not uploaded) is read like any run that ended without a usable Result: the Work is retried and charged to `work_recovery` and `work_total`, or waits for a human.
- **Table:** `reallocate_after_pipeline_failure` is taken for Work whose last Claim failed before its agent for a failure of the pipeline; `allocate_work_retry` and `exhaust_recovery` are refused for it.
- **Required:** classify the failures of the jobs after the agent that the contribution cannot cause, and hold and reallocate their Work the same way.

## The review loop's verdict is reported by the run it reviews

- **Where:** `worker.md` (the review loop of its prompt), `review_loop.check`, `worker_gate.validate`, `fork_publish.preflight`.
- **Today:** the worker launches its own reviewers (foreground `pi-subagents` children of its process), writes their context and records their findings in its report. A prompt-injected or careless worker can under-report, drop a P0 finding, or skip a round, and the reviewers run unsandboxed with the process they review, with read-only tools and no destination credential. Trusted code checks the shape of the report, that a round ran, that the digest the report gives for the last round is that of the series that is pushed (the publish-only retry checks it too), and that no P0 finding is open or closed by the round that raised it. For a rewrite the same holds for the digest of its title and description. The digests are the worker's own claim: trusted code cannot verify that the reviews happened or that the reviewers read that series.
- **Table:** `record_publish_success` and `reject_patch_proposal` of `development.agent_running` state that a Result whose review loop left a P0 finding open, or reports none, is a rejected proposal.
- **Required:** an independent check that the loop ran on the pushed series (for example the reviewers' own Results in the native queue), or a decision that the worker's account is enough.

## The review loop comment is posted once, without retry

- **Where:** `review_loop.py` (`comment`), the step "Post the review loop summary on the pushed commit" of `worker.md` and `publish-retry.yml`.
- **Today:** the summary of the loop is posted as a comment on the pushed commit by the publish job after the push, with the fork token, once. A failed post is only logged: no receipt, no alert, no later attempt, except that a publish-only retry of the same Result posts it too and finds an earlier one by its marker. A contribution whose push never needs a retry and whose post failed has no summary on its development PR.
- **Table:** not a row of the table; the post changes no state.
- **Required:** nothing, by the owner's decision that a failed post is only logged.

## Work queued with its task inline is still accepted

- **Where:** `task_file.resolve`.
- **Today:** the queue carries a reference to the task file of a Work (`task_file`). A Work queued before task files existed carries its task inline (`instructions` and no `task_file`), and every reader accepts it unchanged, so a Work in flight when the change was deployed can finish. No Work is queued that way any more.
- **Required:** remove the inline form once the queue replay shows no live graph with an inline payload.

## Steering edits whose last editor is unknown

- **Where:** `collect.steering`, `collect.edits_unverified` and `steering.new_evidence`.
- **Today:** the REST API does not name who last edited a comment, a review or an issue description, and the collector reads no GraphQL (whose `userContentEdits` would name the editor). On the control repository and the fork, write access is part of the command authority's trust: an edited description, comment or review of an authority account steers whoever edited it. On the upstream PR, an authority account's comment or review comment edited after it was written, and a new version of its review, is recorded with `authority` false (`edit_unverified`) and never steers, even when the owner edited it: the owner steers again by writing a new comment, and the version recorded before the edit still steers. A comment there edited before it was first collected is not trusted either (its `updated_at` differs from its `created_at`), but a review carries no edit time, so one edited before it was first collected looks unedited and is trusted.
- **Required:** a read of the last editor (GraphQL `userContentEdits` with the workflow token) so that an edit on the upstream PR by the author steers and an edit by anyone else does not.

## The rows of an operation are taken through their own engine

- **Where:** `recovery.apply_operation`, `recovery.mark_applying`, `recovery.mark_result`, `recovery.record_discovery`, `recovery.resolve` (the operation table, `lifecycle.OPERATIONS`).
- **Today:** a row of the contribution table is taken only through `engine.try_apply_transition`, whose refusals are a closed set that every call site handles as `engine.HANDLING` declares. The rows of the operation table are taken by `recovery.apply_operation`, which still returns an accepted flag and a free-text reason; its callers raise on a refusal, or try the next row of a resolution.
- **Table:** every status change of an operation is a row of `lifecycle.OPERATIONS`.
- **Required:** the same closed set of refusals and declared handling for the operation table.

## CI never starts on an existing development PR

- **Where:** `development.waiting_ci`; `controller.tick` (the CI bootstrap).
- **Today:** a development PR is recorded, its CI bootstrap was confirmed (or the PR was not created at the recorded head, so none is planned), and no CI run ever appears on the head. Nothing in `development.waiting_ci` notices: the wait has no deadline and no reminder, since CI itself ends it. A human sees it on the status page and uses `/upstreaming refresh` or `/upstreaming park`.
- **Table:** no row of `development.waiting_ci` reads the absence of CI.
- **Required:** a deadline for CI to start on the exact head, and a row to a human wait (the handoff's `require_clean_head_ci` made phase-neutral, through `lifecycle.HISTORIC_NAMES`, would add no verb).

## The HTTP cache is restored from a cache every job on main can write

- **Where:** the "Restore the HTTP cache" step of the `reconcile` job in `controller.yml`; `collect.py` (`PORTING_HTTP_CACHE`).
- **Today:** the cache of the controller's reads is restored from `actions/cache`, which every job running on `main` can write, including the planner and worker agents, which run outside the sandbox and can reach the runner's Actions runtime token. An entry planted with a real validator (`ETag` or `Last-Modified`) and a forged body is served after a 304. The open-time checks of `collect.py` (rows without validators, null or future expiry, unreadable rows, redirect aliases, the 64 MiB bound) do not detect it. The owner accepted this risk.
- **Table:** not a row of the table.
- **Required:** a signature over the file, made and checked with a key only the `reconcile` job holds, or sandboxing the planner and worker agents so that they cannot reach the runtime token.

## Readings to confirm

These follow the literal reading of a decision and are kept until a decision says otherwise:

- "The pipeline code changed since the pause" (the controller's `resume_pause`) compares `paused_at_commit` with `reconcile.pipeline_version`, the SHA-256 of the top-level git tree of `HEAD` without `.state`, not with a commit: the controller checks out one commit, where the last commit that touched the code cannot be read. Any change outside `.state` counts, documentation included, and a run where git cannot read the tree resumes nothing.
- A loaded record that breaks an invariant other than the development PR of `development.waiting_ci` heals by the controller's stop (`invariant_violation: ...`), not by a row of its own; the alert and the report name the invariant.
- An explanation-only comment posted while development Work is due is not recorded: `development.fix_needed` has no `record_explanation` row.
- Feedback that is pending when CI passes is answered by repair Work even when a human push to `riscv64-dev` may already have addressed it: only a published Result clears pending feedback, so a `no_change` outcome of that Work counts as `reject_patch_proposal` and charges `no_progress`, ending in the automatic refresh and then a park.
- "The Work graph is terminal without a usable Result" holds for a cancelled graph at once; for a completed graph when a publication collected in the tick names the Work and left it requested, when its bound worker run ended (or is gone) without an unexpired `porting-publication` artifact, when the queue binds no run to it, or when the artifact exists but was not collected within 60 minutes of the end of the run; while the run is not ended or was not read, nothing is decided and nothing is charged.
- "The failed jobs are rerun on the exact head" (`request_ci_rerun`) holds for a receipt `rerun` (the new attempt of every run read back), and also for `superseded` (a run on the head is in progress on a later attempt, or the run the recorded evidence names has a newer attempt, and no other completed run on the head holds a failed job) and `nothing_to_rerun` (no failed job on the latest attempts): the row is taken and charges `flaky_reruns`, and with nothing rerun the same failing evidence is recorded again by `record_ci_failure`. A `no_change` outcome without a valid receipt, where `request_ci_rerun` applies, is read as "publication failed with an infrastructure error" (`schedule_publish_retry`, `exhaust_recovery`); this holds for the `no_change` Result of `development_patch` Work as for `development_repair` Work, since the trusted publication job reruns for both (`ci_rerun.DEVELOPMENT_WRITE_TASKS`). The repair attempt charged when the Work was allocated is not refunded: the row charges `flaky_reruns` only.
- `rerun_interrupted_ci` is not taken while the contribution is paused or while an operation of the contribution is open: the observation reads CI again. A `ci_rerun` operation that fails (a `stale` or `refused` receipt, launches spent without a receipt, or an operation that no longer matches the record) is closed and fires no row; the next observation of interrupted CI takes `rerun_interrupted_ci` again, charging `interrupted_reruns` again, or `exhaust_interrupted_reruns`. A planned `ci_rerun` operation of a paused contribution is closed the same way once the time its run needs has passed since its last launch (`controller.DEV_PR_RUN_SECONDS`, `handoff.RUN_SECONDS` in `handoff.waiting_ci`; a never launched one at once, and a held one is launched no more), because the workflow refuses a record paused at the launch: it never holds `park` or a `resume` after `refresh.stale_after_days` open, and the first observation after `resume_pause` takes `rerun_interrupted_ci` again within the budget. This holds in `development.waiting_ci` and in `handoff.waiting_ci`; there, passing CI on the clean head behind an open operation keeps the wait, as it defers nomination in development. The launches of its `ci_rerun` operation are repeated within the limit of `operation_launch`, counted on the operation, without charging a budget of the record.
- "A required CI job on the exact head was cancelled or lost its runner" reads a lost runner from the failure-level annotations of a failed job against fixed messages (`ci_rerun.RUNNER_LOST`, pinned by `tests/fixtures/runner-lost-annotations.json` with the messages GitHub documents); they have not yet been checked against the annotations of a real lost run of a contribution fork, so until the owner confirms them a lost runner may still read as an executed failure (`record_ci_failure`), while a cancelled job is rerun. A blocking job that no required pattern names and that lost its runner is interrupted too: unclassified, the gate reads it as failed, so development never nominates a head with it. A workflow could write such an annotation to obtain reruns, bounded by `interrupted_reruns` and then a human wait.
- "The work-queue Policy was installed after the dispatch failed, and the compiled policy preserves it" is read from the validating replay of the ledger: the publication time of the request that installed the current Policy epoch is after `pending_human_action.requested_at`, and the installed Policy declares no worker profile that the compiled dispatcher policy drops. The cause of the failure itself is not recorded, so a dispatch that failed for another reason before a reinstall is re-armed once too; it is charged again by `dispatch_recovery`. While the installed Policy drops a compiled profile and the queue is not quiescent, a dispatcher run that ended is not decided; it is counted by the first decision once the queue is quiescent.
- A planned development PR operation of a paused contribution that was never launched, or launched longer ago than its run needs (`controller.DEV_PR_RUN_SECONDS`; one launched less ago is held and launched no more, so the receipt of an operation launched before the pause completes its transition: the owner's decision of 2026-11-24), or one that is no longer the record's intent (`dev_pr.intent_problem`: another state, revision, fork, head or base, or a PR already recorded for a create, or none for the CI bootstrap), is closed as failed and released without a row, and a new one is planned when a published head in `development.publishing` or `development.fix_needed` again has no PR (a re-plan of a closed intent at the same revision adds `replan:<n>` to its reason ids). A verified receipt that arrives in a state without a row for the operation closes the operation and keeps the state, without recording the PR. Closing an operation after spent launches (`exhaust_development_pr_launches`) does not prove the PR was not created: the next create adopts an open PR that carries this contribution's marker, of any revision or head. The rows of `development.fix_needed` that open the PR also need `work_total` to remain: while it is exhausted nothing is planned or launched (a deferral in the report), and the Work loop takes `exhaust_work_total`.
- A release is a candidate only when every file of it was uploaded at or after the merge time and its tag `v<version>` or `<version>` contains the merge commit; for several distributions every one must be covered. A distribution PyPI does not know needs an operator; a failed read is retried by the next tick.
- The submission package's title and description are the reviewed ones; a reviewed title that is empty once cleaned is `Add riscv64 support`. The package states in the comment, not in the description, how many required CI jobs passed and on which head.
- Handoff receipts are read only from completed `handoff.yml` runs on `main` dispatched by `workflow_dispatch`, and only for the open operation the record runs.
- The workflow posts the submission package only while `riscv64` resolves to the clean head; a package already posted is found by its marker and read back without that check.
- A `riscv64` that is missing when the fork cannot be read under its recorded id is not a moved branch: the attempt is an infrastructure failure (`retry_submission_comment`). A branch that moves after the package is posted is not read in `handoff.preparing_submission`; the locked wait verifies the upstream PR at the exact clean head.
- `/upstreaming retract-pr` takes the revision and the head only. The spec's form also carries `reason="..."`, but `retract_submission` reads no reason, so the grammar refuses it.
- The submission package names the revision of the record when it was posted in its `retract-pr` command; after a pause and its resume, the command of the latest tracking-issue entry carries the current revision, as the package states.
- The submission package asks for no change to the series: a change the contribution policy needs (a CHANGELOG entry, a commit sign-off) withdraws the package with `retract-pr`, and only steps outside the series (such as signing a CLA) are the human's before submitting.
- In the proposed title and description every at sign that could start a mention gets a word joiner (U+2060) after it, whatever the Markdown around it, so the upstream pull request notifies nobody; the package says so.
- A worker reproduction is the build and test run directly in the exact riscv64 image (`docker run --platform linux/riscv64` of the exact reference); the worker gate accepts `patch` and `no_change` only with a passing direct command. `gh act` is optional, its workflow and runner-mapping evidence is recorded only when used, and its failure is advisory: it never blocks an outcome whose direct commands passed, and alone it is no reproduction infrastructure blocker. A proposal or `rehearsal` evidence stored with `workflows` and `runner_mappings` (such as `rehearsal-closeio--ciso8601--1-r3-44982902579`) stays valid.
- A plan stored before the contribution guidelines were part of the contract (schema version 1, such as the plan of `closeio--ciso8601/1`) stays the verified plan of its record: it records no measurable rules, so the worker gate checks no commit rule for it. A new planning run, a refresh included, must record them, and the gate refuses a plan of version 1 from any planning run after the change, also one recovered from an earlier run.
- Resolution evidence is the authorized `/upstreaming resolve-operation` command itself, which the controller records as a `resolution` evidence record with its snapshot of the operation. The pipeline does not verify the human's statement: the disposition is the human's, and the evidence makes it auditable. Any of the three dispositions is accepted from any open status, also `not-launched` for an operation with counted launches.
- After exhausted provisioning launches the planned operation stays open and fences `park` and the stale resume until a resolution or a receipt closes it; a resolution in the wait only closes and releases it, after which `park` and `resume_stale` apply, also from a pause.
- `resolve-operation` is accepted only on the tracking issue of the operation's contribution.
- A provisioning operation resolved `not-launched` or `confirmed` in `provisioning.idle` fires no row (`confirm_provisioning` needs the receipt and its readback): the record releases it and the controller plans the intent again as a new operation (`replan:<n>`), launched within its own `operation_launch`; once 20 re-plans at one revision are closed, `require_provisioning_intervention` takes the human wait with `provisioning_launch_exhausted`, whose resume starts a new revision.
- A resolution that fires no row stages no event, so the tracking issue shows only the command's reaction and reply; the receipt and the `resolution` evidence record are its audit trail.
- A `reason` is bounded at intake to 2000 characters as stored, where each U+2014 counts as the two hyphens it is stored as; a longer one rejects the command.
- A handoff operation that a human resolves with `resolve-operation` fires no row: the confirm rows need the receipt and its readback, and the retry and exhaustion rows a reported failure. The record releases the operation and the controller plans the next attempt, which finds `riscv64` or the package already in place and reads it back.
- A plan below schema version 4 records no series requirement, so nothing is checked before nomination for it. That is true of the live `closeio--ciso8601/1`, whose missing CHANGELOG entry is found by the submission rewrite or its review and returned as feedback.
- A series too large to read in one comparison (more than 50 commits, or 300 files or more) is nominated without its series requirements checked; the event of `nominate_for_handoff` says so, and the submission rewrite and review remain the check.
- When actionable feedback is already pending as CI passes, `return_for_feedback` applies first, and the series requirements are checked the next time CI passes, at the cost of one possible extra Work.
- Series requirements recorded as pending feedback are enforced by the worker gate only while the fork head is the head their evidence names: after a human push, the Work carries the evidence without `context.series_requirements`, and the requirements are checked again the next time CI passes without pending feedback.
