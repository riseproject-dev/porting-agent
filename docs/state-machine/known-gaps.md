# Known gaps between the code and the table
{: .no_toc }

The [lifecycle table]({{ '/state-machine/table/' | relative_url }}) is the source of truth. The places below are where the code does not yet do what the table says, or where `lifecycle check` does not yet catch a violation. Each entry names the table rows involved and the behavior the table requires. Remove an entry in the change that fixes it.

## A repository renamed during upstream review is not followed

- **Where:** `upstream_review.*`; `require_renamed_upstream`, and `resume_upstream_revision` and `resume_renamed_upstream` in `upstream_review.waiting_human`; the collector (`collect.upstream_snapshots`).
- **Today:** when the upstream repository is renamed or transferred while the upstream PR is open, GitHub keeps the PR and answers the recorded repository id under the new name. The collector reports the new name, and once revision Work is due in `upstream_review.fix_needed` the controller takes `require_renamed_upstream` at once. The record keeps `upstream.full_name`, which also names the contribution id, its project, and the intake dedupe, so no row rebinds it: the only route is park, abandon, and a new request for the new name, which opens a second upstream PR for the same change.
- **Table:** `require_renamed_upstream` leads to the human wait with `upstream_unavailable` and no counter, and `resume_renamed_upstream` leaves it only once the repository is read under its recorded name again; a resume before then waits again at once.
- **Required:** a table decision to follow a repository rename while the upstream PR is open, verified by `upstream.repository_id` equality (for example rebind `upstream.full_name` and the PR URL, keeping the contribution id and project under the old name).

## Release acceptance has no recorded contract

- **Where:** `release_wait.idle`; `release.acceptance_contract` and the release observation in `observe_ci.py`.
- **Today:** the acceptance contract is read from the target contract the record names (`target_contract_id`, its `distributions` and `release_rows`), but nothing records a target contract, so every contribution that reaches `release_wait.idle` takes `require_release_intervention` with the pending action `release_contract_missing`. Its resume (`resume_release_observation`) returns to `release_wait.idle`, which asks again at the next observation. The wait has reminders; `park` does not apply in `release_wait.*`, so the contribution stays there until a contract exists.
- **Table:** `verify_release` requires verified release coverage that satisfies the acceptance contract; `release_wait.*` has no other exit.
- **Required:** a producer of the frozen release matrix (the target contract's distributions and rows) before a contribution reaches `release_wait`, and a table decision on how a contribution leaves `release_wait` when the release can never be verified.

## Release verification does not run the install probe

- **Where:** `verify_release` in the release observation; `probe.py`.
- **Today:** release coverage is verified from the official PyPI metadata (non-yanked wheels with a digest, uploaded after the merge, whose tags cover every row) and the provenance of the release tag (it contains the merge commit). The wheels are not downloaded, inspected, installed, or imported; the evidence record says so in its limitations.
- **Table:** `verify_release` requires "verified release coverage satisfies the acceptance contract".
- **Required:** a decision on whether release acceptance requires the install-and-import probe in a clean target environment, then a trusted probe run before `verify_release`.

## Release coverage is read from PyPI only

- **Where:** `release_wait.idle` (`verify_release`, `require_release_intervention`, `record_release_incomplete`); `release.py`.
- **Today:** planning and development serve projects of any language, but the release observation reads release coverage from PyPI only. A contribution whose project releases through another channel (crates.io, npm, Go modules, Maven, container images, GitHub releases, distribution packages) can never have its release verified from that channel, so it waits in `release_wait.waiting_human` for an operator, like a contribution without a recorded contract.
- **Table:** `verify_release` requires verified release coverage that satisfies the acceptance contract, whatever channel the project releases through.
- **Required:** a trusted reader of the release channels the plan records in `project.release_channels`, and the acceptance contract for them.

## Provisioning and development PR operations validate the checked-out state only

- **Where:** `provision.yml` (`python -m provisioning`) and `dev-pr.yml` (`python -m dev_pr`, and `python -m ci_rerun operation` in development).
- **Today:** each job checks out the commit the run was dispatched at and validates the operation against that checkout only; it does not check that the checkout is the head of `main`, and it does not read the head of `main` again before its write. A pause, a `read_only` policy, or a closed operation committed to `main` after the dispatch is not seen, so the write can still run once. The handoff workflow has both checks (`handoff.current_state` before the token, `handoff.unchanged_on_main` before each write).
- **Table:** `pause` stops new Work and writer admission; the operations run only while the policy permits the write and the operation is the record's current planned intent.
- **Required:** the same checks as the handoff workflow (the checkout is the head of `main` before the token, and the state of the operation is unchanged at the head of `main` immediately before each write), or a decision that the window is acceptable.

## The planner and worker agents run on the runner, outside the sandbox

- **Where:** `planner.md` and `worker.md` (`sandbox.agent: false`, `features.dangerously-disable-sandbox-agent: true`, `strict: false`, `tools.bash: ["*"]`); their `agent` jobs; the steps after the agent in those jobs.
- **Today:** no AWF sandbox or firewall runs for these agents. They run as the runner's user on the runner itself with a full shell, so `network.allowed` is not enforced (any host is reachable, and anything read can be sent anywhere), and the runner's user has passwordless sudo on the GitHub-hosted runner and is in the `docker` group, so it can become root directly with `sudo` or through Docker. Every step after the agent in the same job runs code the agent could have replaced: gh-aw's own steps load their scripts from `${RUNNER_TEMP}/gh-aw/actions`, `run:` steps find `bash` and every command on the runner's PATH, and "Configure Git credentials" runs git in the workspace. Those steps hold `ANTHROPIC_API_KEY`, `GH_AW_GITHUB_MCP_SERVER_TOKEN`, `GH_AW_GITHUB_TOKEN` and the job's `GITHUB_TOKEN` ("Redact secrets in logs", the rate-limit and git credential steps), and, as actions, the run's artifact token, so the agent can take them, and through Docker it can also read the provider key the Pi provider patch keeps in the Pi process and the gateway's GitHub token. The job's `GITHUB_TOKEN` is read-only (`actions`, `contents`, `issues`, `pull-requests`). The agent can also write the agent artifacts in any form. What holds is the job boundary, and only while `GH_AW_GITHUB_TOKEN` and `GH_AW_GITHUB_MCP_SERVER_TOKEN` are unset or read-only: the `safe_outputs`, `record`, `notify` and `publish` jobs run on fresh runners, check the native Result, the plan gate or the worker gate and the trusted state again, and only they hold write tokens. The repository expects both unset, so that gh-aw falls back to the job's read-only `GITHUB_TOKEN`: `.github/repository-settings.json` declares no repository secrets and only `ANTHROPIC_API_KEY`, `RISEPROJECT_APP_PRIVATE_KEY` and `RISEPROJECT_UPSTREAMING_APP_PRIVATE_KEY` among the organization secrets selected for it. `scripts/audit_repository_settings.py` compares a settings snapshot with that declaration; CI runs it only on the committed fixture, so a secret added on GitHub is caught only by a live audit, and only if the snapshot lists it. A write token stored under either name would be readable by these agents. The dispatcher is the only workflow whose agent is sandboxed; its agent has neither shell nor file writes, and the home directories its sandbox mounts read-write are owned by root before it runs (`~/.local/bin`, where its rootless AWF is installed first on PATH, among them; the planner and worker install no AWF).
- **Table:** not a row of the table; the trust boundary the workflows rely on for every effect.
- **Required:** an owner decision to sandbox them. With gh-aw v1.2.2 and AWF v0.29.11: the planner needs `sandbox.agent` on (the Docker runtime) and `strict: true`, a `network.allowed` list that covers its web research (the `pi-web-access` extension reaches arbitrary sites, so that is a real restriction), native threat detection becomes available, and the same pre-agent step as the dispatcher (the home directories AWF mounts read-write owned by root, since a sandboxed shell can still write them) plus checks after the agent that run no PATH command and load no code from the workspace. The worker also needs host Docker and QEMU, which the Docker runtime does not give the sandbox: `sandbox.agent.args: ["--enable-dind"]` passes the host Docker socket in, which is root on the runner and bypasses the firewall through new containers, so it contains nothing; `runtime: docker-sudo-iptables` runs AWF privileged with host access; the `cloud-hypervisor` and `nvx` microVM runtimes need KVM on the runner and a Docker and QEMU inside the guest. An upstream fix would let gh-aw run the worker's builds through a trusted Docker proxy outside the sandbox, mount the home tool directories read-only (or not at all) unless a workflow asks for them, and install the rootless AWF outside any directory it mounts.

## Resolution evidence has no producer

- **Where:** `/upstreaming resolve-operation`, guard "a resolution evidence record states the disposition".
- **Today:** the command takes the table's `resolve_*` rows with a record of kind `resolution` from the state store, but nothing writes such a record, so every resolution is refused with "resolution evidence record not found".
- **Table:** `resolve-operation` closes an open operation with a resolution evidence record.
- **Consequence:** after `require_provisioning_intervention` for exhausted launches the planned provisioning operation is still open. Within `refresh.stale_after_days` the resume leaves the wait (`resume_provisioning`). Once the wait is older, `resume_stale` and `park` are refused while the operation is open (both require no open operation), and only a resolution or a late receipt that closes the operation lets the contribution leave the wait. A provisioning run that fails without a definite failure (a failed read, a write answered with anything but a definite refusal, a lost runner) writes no receipt, so it reaches this wait through launch exhaustion. A `pause` taken in the wait is accepted, and the resume after it is refused once the stop is stale, so the contribution is then paused and stuck as well. While it is not paused, an operator can run the provisioning workflow again for the planned operation once the cause is corrected; its receipt closes the operation, after which `park` and `resume_stale` apply.
- **Required:** a trusted way to record resolution evidence, or a table decision on the exits of this wait once it is stale (for example `resume_provisioning` without the not-stale guard, or no `pause` in it).

## An accepted Result whose report cannot be stored pauses the contribution

- **Where:** `worker_report.evidence`, `reconcile.report_evidence` in the folds of the six rows of `reconcile.REPORT_VERBS`, and `reconcile.pushed_report_evidence` in the folds of a Result whose push may have landed (an `uncertain` Result held for a publish-only retry, a retry rejected as stale behind the operation of an earlier attempt).
- **Today:** a success Result of Work that carries a history always has a report the gate accepted. When the reconciler finds that report missing, unreadable or invalid in the publication artifact, or cannot build its evidence, it raises `worker_report.ReportError` inside the contribution's isolation block: the tick takes `pause_on_processing_error` instead of the success row, with a reason that names the Work. The pause is specific to that contribution (`isolation.ContributionPause`) and any number of them in one tick stop nothing else. The pause clears the Work, so that Result takes `record_late_effect` the next tick, whose event records that its report could not be stored, and the artifact is not acted on again; a publication it made is seen only by head observation after the resume. The report itself cannot be recovered from that artifact.
- **Table:** the six rows store the report of the Work as `worker_report` evidence; no row folds a success Result without its report.
- **Required:** a table decision on an accepted Result whose report is lost after the gate (for example a row that folds it with a recorded loss, or a retry of the publication artifact).

## A publication job lost after its push leaves no report

- **Where:** the publication job of `worker.md` and `publish-retry.yml`, and `reconcile.fold_patch_result`.
- **Today:** the report of a Result whose push may have landed is stored when the Result is folded, whatever ends the hold afterwards. A publication job whose runner is lost after its push and before it uploads the publication artifact, which it uploads even after a failed step, leaves no Result: dispatch recovery or the wait for a publish-only retry ends the Work, the branch observation can confirm the push, and CI runs on that head, but no report of that Work is ever read, so a repair after failing CI on it reads the CI without the report of the worker that left the head.
- **Table:** a held publication ends by a retry Result, the exhaustion of `publish_recovery`, or a stop; no row reads a report from anywhere but a folded Result.
- **Required:** the report uploaded before the push (for example in a separate artifact the reconciler reads when the branch observation confirms an operation whose Result never arrived).

## A long request description makes its Work undispatchable

- **Where:** `work.payload` and `work.cmd_plan`.
- **Today:** every Work payload carries the frozen tracking issue description in `context.tracking_issue`, and intake admits a description of up to 16384 bytes (`intake.max_request_bytes`), while the dispatcher keeps a payload within 15500 bytes (`work.MAX_PAYLOAD_BYTES`) of the queue's limit of 16384. The rest of a payload takes about 2 KB with its history reference, more with reason evidence, so a description over about 13 KB makes a payload over the budget. The dispatcher skips that one Work and reports it (`skipped`), and dispatches every other Work; the skipped Work is never claimed, so dispatch recovery relaunches the dispatcher (`retry_dispatch`) and then waits for a human (`exhaust_dispatch_recovery`). The controller measures the smallest payload of the Work as the dispatcher builds it from the committed evidence (`work.payload_floor`), so both events, and the tracking issue entry of the wait, name the cause: the payload size, the size of the frozen description, and the length a new request must keep to. The frozen description cannot change, so the human can only make the request again with a shorter description.
- **Required:** the description passed by reference like the history (the frozen description in the committed contribution record at the pinned commit, fetched and verified by the trusted pre-agent step and by the trusted gates that check it, such as the plan gate's description digest), or an intake limit that leaves the payload room.

## Steering edits whose last editor is unknown

- **Where:** `collect.steering`, `collect.edits_unverified` and `steering.new_evidence`.
- **Today:** the REST API does not name who last edited a comment, a review or an issue description, and the collector reads no GraphQL (whose `userContentEdits` would name the editor). On the control repository and the fork, write access is part of the command authority's trust: an edited description, comment or review of an authority account steers whoever edited it. On the upstream PR, an authority account's comment or review comment edited after it was written, and a new version of its review, is recorded with `authority` false (`edit_unverified`) and never steers, even when the owner edited it: the owner steers again by writing a new comment, and the version recorded before the edit still steers. A comment there edited before it was first collected is not trusted either (its `updated_at` differs from its `created_at`), but a review carries no edit time, so one edited before it was first collected looks unedited and is trusted.
- **Required:** a read of the last editor (GraphQL `userContentEdits` with the workflow token) so that an edit on the upstream PR by the author steers and an edit by anyone else does not.

## Work requested before the Work identity carried the generation

A Work payload written before the Work identity carried `generation` and `dedupe_key` names neither: the reconciler and the publisher read it as generation 0 and recognize its Work by its revision (`work.task_identity`), and requested Work recorded without `active_work.generation` is generation 0 (`work.work_generation`) and is dispatched with the payload it was first submitted with. Remove both fallbacks once no such Work or worker is in flight.

## Readings to confirm

These follow the literal reading of a decision and are kept until a decision says otherwise:

- `resume_upstream_review` still clears pending feedback after `answer_reviewer`, although the pending-feedback decision says every resume keeps it.
- An explanation-only comment posted while development Work is due is not recorded: `development.fix_needed` has no `record_explanation` row.
- `record_actionable_review` does not list the processed comment and review ids; the collector records them beside the row.
- The admission scope guard is on `admit_development` only, not on `readmit_development`.
- `resume_stale` from a `provisioning` state, which has no fork, records a refresh with the phase `provisioning` and no head or development PR. The refreshed plan returns to development on the recorded fork only when the refresh began with the fork and development PR the record still holds; otherwise development is admitted afresh.
- `pause_on_identity_change` is guarded by `not paused`: an identity change observed while a contribution is paused sets nothing; the controller still selects no Work for it while the identity differs.
- The reminder interval is counted in whole days from the exact time of the request or of the last reminder; a day counts when it ends on a weekday (UTC). Any pending action in a human wait of the table gets reminders.
- A reminder is suppressed while paused and counted from the request, so after a long pause the resume and an overdue reminder can be posted in the same tick.
- `/upstreaming resume` on a contribution that is neither paused nor in a human wait or in `parked.idle` is answered with `not paused`.
- Feedback that is pending when CI passes is answered by repair Work even when a human push to `riscv64-dev` may already have addressed it: only a published Result clears pending feedback, so a `no_change` outcome of that Work counts as `reject_patch_proposal` and charges `no_progress`, ending in the automatic refresh and then a park.
- `/upstreaming resume` in `parked.idle` that is not paused is rejected with the refresh form (`/upstreaming refresh revision=N reason="..."`, with `class=` and `paths=` for an admission override); when paused it clears the flag only.
- `/upstreaming refresh` from `parked.idle` records `admission_override` only when it names both `class` and `paths`; the override's reason is the refresh's reason. A refresh that names only one of them is refused when it is posted and changes nothing, because such an override could never admit development. Every other refresh refuses `class` and `paths`, and a resume that names them is rejected when it is parsed.
- `abandon` records `terminal_reason` `abandoned`; the reason the human gives is kept in the event only. A paused record stays paused when it is abandoned, and a later `resume` of the closed record takes `resume_pause`, which clears the flag and changes nothing else (the clearer of the flag has no terminal guard).
- A command field that the row taken does not read is refused, not ignored: `head` on a `refresh` outside `handoff.waiting_upstream_pr`, `class` and `paths` on a `refresh` outside `parked.idle`.
- A contribution skipped by a tick, after a collector failure or an unexpected error, leaves every command on its tracking issue, `resume` included, unconsumed and without a reply until a tick processes it. An error in a contribution that is already stopped, or that the same tick would have created, is reported in the tick report (`controller.alerts`) and the workflow annotation only, with no event and no post on the tracking issue.
- `begin_planning` is taken in the tick that allocates the planning Work (or exhausts its budget), not as soon as a request is in `queued.idle`: a request waiting for a worker slot stays in `queued.idle`, where removing the intake label still withdraws it.
- The task that `request_patch` asks for is a patch, or a repair when feedback is pending for the Work to answer; `request_repair` always asks for a repair. A refreshed plan that returns to the fork without a failing CI job or pending feedback is therefore answered by a patch.
- Every rejected or blocked outcome charges `no_progress`, whatever progress the worker reports, because `reject_patch_proposal` charges it unconditionally; a published Result starts it again, as `BUDGETS` states, although no row lists that restart.
- The failing CI job of the head is the first executed blocking job of the evidence at `last_ci_evidence_id` that did not succeed, else the first job the evidence names as failing the runner-label check. Its name is the key of `budget.clusters`; existing keys are kept.
- A Work payload without `generation` and `dedupe_key` is generation 0, also when the record is in a later generation: its Result is then late. A payload that names only one of them matches no Work.
- While the record holds requested Work, or a Result held for a publish retry that is not exhausted, a changed fork head is not recorded; the table has no head row in an `agent_running` state.
- `exhaust_work_recovery` names `work_total` when both budgets are exhausted.
- "The Work graph is terminal without a usable Result" holds for a cancelled graph at once; for a completed graph when a publication collected in the tick names the Work and left it requested, when its bound worker run ended (or is gone) without an unexpired `porting-publication` artifact, when the queue binds no run to it, or when the artifact exists but was not collected within 60 minutes of the end of the run; while the run is not ended or was not read, nothing is decided and nothing is charged.
- In upstream review, `exhaust_repair_attempts` names the first exhausted counter of `no_progress`, `work_total`, and `repair_attempts_cluster`.
- A wait for a human is a state of kind `gate` or `locked`, or of kind `human_wait` with a recorded pending action (`engine.waits_for_human`). Only the rows the table lists for it leave it: observation reads nothing in a wait that has no observation row, no write beside a row can change its phase or activity, and a Result that arrives there takes `record_late_effect`. No code writes a `waiting_human` activity without a pending action; no resume applies to it, and `park` leaves it.
- A planned operation that a trusted workflow runs stays `planned` across its launches; `begin_effect`, `record_response`, and `confirm_by_discovery` are taken together when its verified receipt is folded with the exact readback. The receipt establishes the facts of `begin_effect` (capacity available, the contribution not paused, the final check passed): the workflow's own final check read them before the effect. A push establishes "capacity available" without a runner reservation.
- A branch operation that the store holds as `applying` lost the response of its push: the branch observation takes `record_response` ("its response was lost") before discovering it, as the publisher hands an operation over only after it recorded the response.
- When the publisher's final check before a push does not pass (the head re-read fails or moved), no intent is recorded and the outcome carries no operation, instead of a `failed` operation, because `planned` has no row to `failed` other than a resolution.
- `active_operation_id` names an open operation only: the reference is released in the write that closes the operation, although no row of the table lists that clear (`record_merge` clears it explicitly).
- The counter of `operation_launch` is `external_ids.launch_attempts` of the operation, where launches were counted before the table. A launch is repeated only 300 seconds after the last one, and the relaunch requires available capacity, like the first launch. A development PR operation is launched by `launch_development_pr` within the same limit, without a capacity guard.
- `require_provisioning_intervention` for exhausted launches is taken once the last allowed launch is 300 seconds old without a receipt, and not while the contribution is paused. Its pending action is `provisioning_launch_exhausted` with the counter `operation_launch`; after the provisioning operation failed (a human resolves it `failed`, or a verified receipt reports a definite failure), it is `provisioning_operation_failed` without a counter.
- A human `/upstreaming resume` in `provisioning.waiting_human` whose pending action is one the controller writes there (`provisioning_launch_exhausted` with the counter `operation_launch`, or `provisioning_operation_failed`) is the human's assertion that the prerequisite is corrected: the controller establishes "the prerequisite is corrected" for that command. Another pending action in that wait establishes nothing.
- After the resume of exhausted launches the same planned operation is launched again, from a launch count of zero, although the resume bumped the revision; the provisioning workflow accepts an operation of an earlier revision when the record names it as its active operation, and the receipt carries the record's revision.
- A verified provisioning receipt whose status is `failed` reports a definite failure of the effect; it is folded only for a `planned` or `applying` operation of a record in `provisioning.idle` (which fires `require_provisioning_intervention`) or in `provisioning.waiting_human` (which keeps the wait). A receipt with any other status than `provisioned` or `failed` (a `refused` one among them) is not folded, and of several foldable receipts for one operation only the newest run's is folded.
- The attempt that makes the operation of a publish-only retry its own is the attempt the retry was dispatched with (`UPSTREAMING_PUBLISH_ATTEMPT`); the first attempt adds nothing, so its id is unchanged. A CI bootstrap `dev_pr_update` planned again counts the earlier ones for the same head that the store holds.
- An operation the tick stages that the state publisher's check would refuse is an unexpected error of its contribution (step `operation_check`): the contribution is paused by the controller and the commit goes ahead for the others.
- A provisioning operation resolved `confirmed` by a human fires no row: `confirm_provisioning` needs the receipt and the readback. A receipt that arrives while the contribution waits for a human closes the operation and keeps the state.
- A record whose `last_ci_evidence_id` names evidence that the store does not hold, in a state where Work is allocated, is an unexpected error of that contribution and takes `pause_on_processing_error`; the pause names the missing evidence id.
- `park_planning` records `previous_phase` `planning` and keeps a recorded refresh; like every row that ends the generation it does not bump the revision. `parked_reason` is the plan's rationale.
- An admission override applies against a decision park only when it names both a class and paths; one that names only one of them (recorded before such a command was refused) does not admit, and the Result takes `reject_plan`, so the next planning runs with the override still recorded, within `planning_attempts`. The override's paths are the human's scope: the plan's path coverage is recorded for them in `scope_coverage_complete` but does not refuse them. With a decision develop the plan's class and paths are admitted and the override is cleared.
- "The verified plan names `scope_paths`, and `scope_coverage_complete` holds" is established when the admitted scope has an admission class, names 1 to 32 safe scope paths, and matches every path of the plan's `path_coverage`; a plan without `path_coverage` has an incomplete scope. `admit_development` and `readmit_development` do not list `scope_coverage_complete`; the reconciler records it beside the row, as repair Work reads it.
- A worker outcome `proposal`, which no publisher produces any more, is folded as an outcome rejected in trusted validation.
- A Result of Work that the record holds but that its phase does not request (planning Work outside `planning`, patch Work outside `development`, revision Work outside `upstream_review`) is late, and so are a plan outside `planning`, any other Result in `planning`, and the Result of a held publication outside `development` and `upstream_review`.
- A held publication whose `publish_recovery` is exhausted (`pending_publication.exhausted`) launches nothing more and is not a pending publication for the quiescence guard ("no pending publication"), so `resume_development` and `resume_stale` apply to the wait `exhaust_publish_recovery` entered, and clear it.
- The Result of a publish-only retry ends the held publication: `pending_publication` is cleared beside the row that folds it (`record_publish_success`, `reject_patch_proposal`, `replan_development`, `request_ci_rerun`), although none of those rows lists that clear.
- `record_publish_success` adds the published files to `scope_paths` beside the row, as a repair backed by review feedback may change a path the plan missed.
- The worker's `no_change` report is "a failure not caused by the patch" for `request_ci_rerun`: it takes the row when the Work carries no feedback (`active_work.feedback_evidence_ids`; the Work's `reason_ids` are not feedback) and `flaky_reruns` remains for the head, and counts as `reject_patch_proposal` otherwise. The row keeps the revision, so the Work id names the head's `flaky_reruns` count from the first rerun on, and the repair Work requested after a rerun is never the Work whose Result requested it. A blocked Result's rehearsal evidence is stored and named in the event, and is not recorded as pending feedback, since no row sets it; a rehearsal id that the code before the table recorded as pending feedback still holds `nominate_for_handoff`.
- "The failed jobs are rerun on the exact head" (`request_ci_rerun`) holds for a receipt `rerun` (the new attempt of every run read back), and also for `superseded` (a run on the head is in progress on a later attempt, or the run the recorded evidence names has a newer attempt, and no other completed run on the head holds a failed job) and `nothing_to_rerun` (no failed job on the latest attempts): the row is taken and charges `flaky_reruns`, and with nothing rerun the same failing evidence is recorded again by `record_ci_failure`. A `no_change` outcome without a valid receipt, where `request_ci_rerun` applies, is read as "publication failed with an infrastructure error" (`schedule_publish_retry`, `exhaust_publish_recovery`); this holds for the `no_change` Result of `development_patch` Work as for `development_repair` Work, since the trusted publication job reruns for both (`ci_rerun.DEVELOPMENT_WRITE_TASKS`). The repair attempt charged when the Work was allocated is not refunded: the row charges `flaky_reruns` only.
- `rerun_interrupted_ci` is not taken while the contribution is paused or while an operation of the contribution is open: the observation reads CI again. A `ci_rerun` operation that fails (a `stale` or `refused` receipt, launches spent without a receipt, or an operation that no longer matches the record) is closed and fires no row; the next observation of interrupted CI takes `rerun_interrupted_ci` again, charging `interrupted_reruns` again, or `exhaust_interrupted_reruns`. A planned `ci_rerun` operation of a paused contribution is closed the same way, since the workflow refuses a paused record and no receipt can arrive: it never holds `park` or a `resume` after `refresh.stale_after_days` open, and the first observation after `resume_pause` takes `rerun_interrupted_ci` again within the budget. This holds in `development.waiting_ci` and in `handoff.waiting_ci`; there, passing CI on the clean head behind an open operation keeps the wait, as it defers nomination in development. The launches of its `ci_rerun` operation are repeated within the limit of `operation_launch`, counted on the operation, without charging a budget of the record.
- "A required CI job on the exact head was cancelled or lost its runner" reads a lost runner from the failure-level annotations of a failed job against fixed messages (`ci_rerun.RUNNER_LOST`, pinned by `tests/fixtures/runner-lost-annotations.json` with the messages GitHub documents); they have not yet been checked against the annotations of a real lost run of a contribution fork, so until the owner confirms them a lost runner may still read as an executed failure (`record_ci_failure`), while a cancelled job is rerun. A blocking job that no required pattern names and that lost its runner is interrupted too: unclassified, the gate reads it as failed, so development never nominates a head with it. A workflow could write such an annotation to obtain reruns, bounded by `interrupted_reruns` and then a human wait.
- `publish_recovery` counts the failed publications of the held Result (`pending_publication.attempts`), each charged by `schedule_publish_retry`, so a Result is published at most `retries.infrastructure_per_head_failure` plus two times before `exhaust_publish_recovery`; the launch of a scheduled retry charges nothing.
- A launched publish-only retry whose Result is not folded within 60 minutes of the launch (`pending_publication.launched_at`) is "publication failed with an infrastructure error": `schedule_publish_retry` charges `publish_recovery`, or `exhaust_publish_recovery` waits for a human, as for a lost dispatch. A Result of that retry that arrives later, while the Result is still held and the contribution does not wait for a human, matches the held publication and is folded by its row; in the wait it takes `record_late_effect`. An infrastructure error such a Result reports was already charged by the wait: it takes `record_late_effect` and charges nothing again. A launch is charged once its Result or its wait charges it, so a held Result's `infra_error` is charged already when its attempt (`UPSTREAMING_PUBLISH_ATTEMPT`) is not above `pending_publication.attempts`, or, without an attempt, when no retry is launched.
- Work that an allocation row names under a graph that returned a Result in the same tick or is completed or cancelled in the queue is "the Work graph is terminal without a usable Result": the controller takes the allocation row and then `allocate_work_retry` or `exhaust_work_recovery` in the same tick, so the allocation charges `work_total` and the fresh graph charges `work_recovery` and `work_total` again, and the spent graph is never submitted.
- `dispatch_recovery` counts the dispatcher runs that ended since the Work was requested, or, for Work the queue holds for another attempt after a worker run that ended without a Result, since the queue's retry time (`retry_not_before`); each ended run is decided once (`retry_dispatch` or `exhaust_dispatch_recovery`), and `active_work.dispatched_run_id` names the last decided run. A dispatcher launch that never shows up as a run is launched again after 15 minutes without a row, since no run ended; for a queue retry with no dispatcher run since the retry time, the dispatcher is launched 15 minutes after the retry time, without a row, so a dispatcher run the run list does not show yet is not launched twice. A Work whose `retry_not_before` is no representable time is left out of the retries and reported in the controller log; its dispatch is decided as for any other requested Work.
- "The work-queue Policy was installed after the dispatch failed, and the compiled policy preserves it" is read from the validating replay of the ledger: the publication time of the request that installed the current Policy epoch is after `pending_human_action.requested_at`, and the installed Policy declares no worker profile that the compiled dispatcher policy drops. The cause of the failure itself is not recorded, so a dispatch that failed for another reason before a reinstall is re-armed once too; it is charged again by `dispatch_recovery`. While the installed Policy drops a compiled profile and the queue is not quiescent, a dispatcher run that ended is not decided; it is counted by the first decision once the queue is quiescent.
- In `development.waiting_ci` an actionable review observed with a CI failure in the same tick is recorded (`record_actionable_review`); the failure is not, since `development.fix_needed` reads no CI (its observation rows are `record_head_change` and `record_actionable_review`), and the review would be filtered out once the repair publishes a new head. The repair Work carries the review but no failing CI job.
- "An executed blocking failure on the exact head" (`record_ci_failure`, `return_for_repair`) is established by a CI verdict `failed`, which also covers a required job that ran on a runner without the contract's runner label.
- "The observed development PR does not match the recorded fork, ref, or PR" holds when GitHub has no such PR, or its number, head repository, head ref, or base ref differs from the record's; a closed development PR still matches.
- `nominate_for_handoff` and Work allocation wait while a development PR or CI bootstrap operation is open, although the nomination row has no operation guard.
- A planned development PR operation of a paused contribution, or one that no longer matches the record (another state, revision, fork, head or base, or a PR already recorded for a create, or none for the CI bootstrap), is closed as failed and released without a row, and a new one is planned when `development.waiting_ci` again holds a published head without the PR (a re-plan of a closed intent at the same revision adds `replan:<n>` to its reason ids). A verified receipt that arrives outside `development.waiting_ci` closes the operation and keeps the state, without recording the PR. Closing an operation after spent launches (`exhaust_development_pr_launches`) does not prove the PR was not created: the next create adopts an open PR that carries this contribution's marker, of any revision or head.
- A Result of Work the record holds in a state of the table without a row that folds a Result (for example Work held in `development.fix_needed`) is late.
- `submit_upstream` records `handoff_approval` with the CI evidence and the plan the approval saw (`evidence_ids`); it records no operation. The review Work is allocated in `handoff.review_due` by `request_submission_review`, in the same tick when a worker slot is free.
- The submission rewrite reshapes the commits of the approved series "only if CONTRIBUTING or reviewers require it" for a squash or a split; that requirement is the model's judgment, checked by the separate review Work, and trusted code checks that every commit is valid upstream and holds only content of the base or of the approved series, that the final tree is unchanged, and that the measurable rules, including `max_commits`, hold.
- "The same final tree and no content the approved series does not have" is read as: the tree of every reviewed commit is the tree of a commit of the approved series without its debug commits, later in that series than the tree of the reviewed commit before it. Squashing and rewording are admitted; reordering and content the approved series removed are refused. A split is therefore refused unless every tree it produces is a tree of that series, so a split the project requires sends the submission back to development, where the split commits can be made and approved first.
- The revision is bumped when the rewrite is accepted (`accept_submission_rewrite`), since the review is new Work of the next revision and the revision rule requires a bump on a Result that leads to a state where Work is due; the package names the approval's revision, and the `retract-pr` command it carries names the current one.
- The required CI workflow the build of `riscv64` dispatches on the clean head is the workflow of the latest required CI run on the candidate head (`workflow_path` of its evidence), read at the clean head as data: dispatchable when its triggers include `workflow_dispatch` and none of its inputs is required without a default. A project whose required jobs span several workflows gets that one dispatched; the others run only if a push triggers them, and the bounded wait of 12 hours then asks a human (`require_clean_head_ci`).
- In upstream review the recorded head is `upstream_pr.head_sha` (`lifecycle.recorded_head`), the field the table's `record_head_change` there updates; `fork.head_sha` keeps the approved head of `riscv64-dev`. The head the observation compares is the head of the upstream PR as GitHub reports it.
- Review feedback on the upstream PR is "authorized" when its author is in the command authority, as on the development PR; feedback from other accounts is not recorded, so an upstream maintainer's review reaches the pipeline only through an authorized human.
- "Not yet recorded for this head and CI run" (`record_upstream_ci_failure`) holds when the evidence of the failing run and attempt is not `last_ci_evidence_id`; no row clears that field in upstream review except `record_head_change`.
- In upstream review a proposal rejected as stale takes `reject_patch_proposal` ("the proposal is rejected for the current revision"), since no row replans there; a `no_change` report takes `require_reviewer_answer` also when the revision Work answered a CI failure.
- The upstream PR is read without any change for `upstream_review.waiting_human` with the pending action `pr_closed_unmerged` and for `parked.idle` with an upstream PR: the facts "the upstream PR is observed open again" of the resume and "no open upstream PR" of the refresh are established from that read of the same tick (a merged PR is not open).
- A release is a candidate only when every file of it was uploaded at or after the merge time and its tag `v<version>` or `<version>` contains the merge commit; for several distributions every one must be covered. A distribution PyPI does not know needs an operator; a failed read is retried by the next tick.
- A rewrite is expired once its evidence is one day short of the retention of the publication artifact that holds the series (`handoff.rewrite_expired`), 29 days by default: the artifact is kept 30 days, or the days of the repository variable `GH_AW_DEFAULT_ARTIFACT_RETENTION_DAYS` when it is set (1 to 400; 0 or another value counts as 30), which the controller's workflow passes to the tick; for a retention of one day the margin is half a day. The day of margin covers a review or build that starts just before the expiry. The trusted workflow also refuses an artifact GitHub reports as expired; that attempt fails as an infrastructure failure, and the next plan finds the rewrite expired by its age. A repository or organization retention limit below that value shortens the artifact's life without the tick knowing: the build attempts then fail as infrastructure failures until the rewrite is old enough or the attempts are exhausted and a human is asked.
- A plan of schema version 1 records no measurable rules and no template sections: the submission check then applies the rules and sections the review reports having found in the project. They are untrusted but can only refuse a submission, never admit one.
- A required template section is present when the description has a Markdown heading with the same words (case and emphasis ignored). Whether every checklist item is answered honestly is the review's judgment; the check does not parse checklists.
- CI is a function of the tree: when the reviewed series has the tree of the candidate head, the CI evidence of the candidate head on `riscv64-dev` is CI on the clean head, and `accept_clean_head_ci` records it.
- "An upstream PR is open from `riscv64`" is any open pull request of the upstream repository whose head is `riscv64` of the fork owner, whoever opened it. It is checked only when `riscv64` must be written; a `riscv64` that already resolves to the reviewed head is read back without a write and without that check.
- A failed review, a failed check, or an unusable review Result never posts anything and never writes `riscv64`. `reject_submission_review` keeps `handoff_approval`, like `return_for_repair`; the next `submit_upstream` replaces it.
- The worker gate reads the commit messages of a proposed series from its mbox as `git am` would (the subject without its `[PATCH]` prefix, the body up to the first `---` line); the submission check reads them from the rebuilt commits.
- The handoff operations are launched without a row, like a `ci_rerun` operation: within `operation_launch`, not while the contribution is paused, and never again within 300 seconds of the last launch. After that, an attempt is held (neither launched again nor closed as spent) while the run list of the controller workflow names a `handoff.yml` run of the operation that is not completed, or while the run list could not be read in the tick, for at most `handoff.RUN_SECONDS` (3600 seconds) after the last launch; then it is launched again or closed as before. Launches spent without a receipt are a definite infrastructure failure of the attempt: once the last allowed launch is old enough by that rule with no receipt, and the contribution is not paused, the controller closes the attempt as failed (`begin_effect` and `record_failure`, with the facts of a receipt, although no workflow reported its final check) and fires the retry row of the state or its exhaustion row. A receipt of that attempt that arrives later is not folded; the next attempt finds the effect already in place and reads it back. The receipt of an attempt the workflow refused is not folded either, so refusals count as launches without a receipt. A final check that refuses immediately before a write (the state of the operation changed on `main` after the checkout) is such a refusal. The trusted workflow accepts an attempt of an earlier revision when the record names it as its active operation (a pause and its resume bump the revision).
- The counter of `upstream_branch` and `submission_comment` ("the handoff operation's attempts") is the number of attempts in the current round, recorded on each attempt as `count:<k>`: a failed attempt with a count below `retries.infrastructure_per_head_failure` plus one takes the retry row, which the next attempt (count plus one) charges; at that count it takes the exhaustion row. After the resume of that exhaustion the next attempt counts from one. A pause does not start the count again.
- A build of `riscv64` whose reviewed series does not rebuild to the reviewed head, or whose lease on `riscv64` conflicts (the branch moved between the read and the push), is not charged to `upstream_branch`: it takes `return_for_repair`, whatever the count; one that finds an upstream PR open from `riscv64` takes `require_branch_intervention`.
- When the reviewed series has the tree of the candidate head, `accept_clean_head_ci` can be taken in the tick that confirms the clean head, from the CI evidence already recorded for the candidate head.
- `return_for_repair` from `handoff.building_upstream_branch` and `handoff.waiting_ci` keeps `handoff_approval`, as its row clears only the clean head, the review, `handoff_request`, and the pending action (the row from `handoff.waiting_ci` also records the failing CI evidence of the clean head); the next `submit_upstream` replaces it.
- In the locked wait `handoff_request.command_id` names the submission package operation; the reminder links the comment that operation read back.
- "A compatible human author" of the upstream PR is a `User` account whose id is in `command_authority.actor_ids`; it need not be the human who requested the submission. A draft pull request is open.
- An observation of the locked wait that does not verify the upstream PR is recorded by `record_audit_observation` once per distinct observation (fork head, failing candidates, several matching candidates); every reminder after it states the mismatch the observation of that tick finds.
- The submission package's title and description are the reviewed ones; a reviewed title that is empty once cleaned is `Add riscv64 support`. The package states in the comment, not in the description, how many required CI jobs passed and on which head.
- Handoff receipts are read only from completed `handoff.yml` runs on `main` dispatched by `workflow_dispatch`, and only for the open operation the record runs.
- The workflow posts the submission package only while `riscv64` resolves to the clean head; a package already posted is found by its marker and read back without that check.
- A `riscv64` that is missing when the fork cannot be read under its recorded id is not a moved branch: the attempt is an infrastructure failure (`retry_submission_comment`). A branch that moves after the package is posted is not read in `handoff.preparing_submission`; the locked wait verifies the upstream PR at the exact clean head.
- `/upstreaming retract-pr` takes the revision and the head only. The spec's form also carries `reason="..."`, but `retract_submission` reads no reason, so the grammar refuses it.
- The submission package names the revision of the record when it was posted in its `retract-pr` command; after a pause and its resume, the command of the latest tracking-issue entry carries the current revision, as the package states.
- The submission package asks for no change to the series: a change the contribution policy needs (a CHANGELOG entry, a commit sign-off) withdraws the package with `retract-pr`, and only steps outside the series (such as signing a CLA) are the human's before submitting.
- In the proposed title and description every at sign that could start a mention gets a word joiner (U+2060) after it, whatever the Markdown around it, so the upstream pull request notifies nobody; the package says so.
- A worker reproduction is the build and test run directly in the exact riscv64 image (`docker run --platform linux/riscv64` of the exact reference); the worker gate accepts `patch` and `no_change` only with a passing direct command. `gh act` is optional, its workflow and runner-mapping evidence is recorded only when used, and its failure is advisory: it never blocks an outcome whose direct commands passed, and alone it is no reproduction infrastructure blocker. A proposal or `rehearsal` evidence stored with `workflows` and `runner_mappings` (such as `rehearsal-closeio--ciso8601--1-r3-44982902579`) stays valid.
- A plan stored before the contribution guidelines were part of the contract (schema version 1, such as the plan of `closeio--ciso8601/1`) stays the verified plan of its record: it records no measurable rules, so the worker gate checks no commit rule for it. A new planning run, a refresh included, must record them, and the gate refuses a plan of version 1 from any planning run after the change, also one recovered from an earlier run.
- A handoff operation that a human resolves with `resolve-operation` fires no row: the confirm rows need the receipt and its readback, and the retry and exhaustion rows a reported failure. The record releases the operation and the controller plans the next attempt, which finds `riscv64` or the package already in place and reads it back.
- A plan below schema version 4 records no series requirement, so nothing is checked before nomination for it. That is true of the live `closeio--ciso8601/1`, whose missing CHANGELOG entry is found by the submission rewrite or its review and returned as feedback.
- A series too large to read in one comparison (more than 50 commits, or 300 files or more) is nominated without its series requirements checked; the event of `nominate_for_handoff` says so, and the submission rewrite and review remain the check.
- When actionable feedback is already pending as CI passes, `return_for_feedback` applies first, and the series requirements are checked the next time CI passes, at the cost of one possible extra Work.
- Series requirements recorded as pending feedback are enforced by the worker gate only while the fork head is the head their evidence names: after a human push, the Work carries the evidence without `context.series_requirements`, and the requirements are checked again the next time CI passes without pending feedback.
