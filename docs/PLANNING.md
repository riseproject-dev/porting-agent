# Planning contract

The planner researches upstream history, contribution policy, build and test topology, release mechanics, dependencies, and prior architecture work. The project may be written in any language and planned on its own build, test, and release tooling; the plan records it in `project`: its languages, build systems, how it builds and tests, its release channels with whether each already serves riscv64, and the state of its toolchain on linux/riscv64. The dependency audit covers every build and test dependency and every tool the CI downloads in the project's ecosystem (Go modules and `GOARCH`, Rust targets and `-sys` crates, C and C++ libraries, JDK and JNI natives, JavaScript native addons, container base images); a Python project is additionally audited against public PyPI and the RISE index. That a project has no Python package, wheel, or PyPI release is never a reason to park.

Exactly one planner profile runs through gh-aw v1.2.2 native Work. The controller commits an immutable `active_work` request before launching `dispatcher.lock.yml`. Trusted dispatcher preparation replays that exact request into the native queue; it does not let the model select or mutate Work. Queue admission and dispatch are limited to one `planner.lock.yml` Claim.

The planner uses the scoped `GITHUB_TOKEN` and a server-enforced read-only GitHub MCP server. It has no control App private key, destination token, package credential, fork writer, or repository mutation tool. Required research covers the complete tracking issue and comments, issue and PR history including reviews, CI and release topology, maintainers and contribution rules, the contribution guidelines below, project reports, the project graph, and the riscv64 availability of the project's dependencies in its ecosystem (for a Python project, public/RISE dependency-wheel evidence).

## Contribution guidelines

A plan records, as `contribution_guidelines` (plan schema version 2 and later), how the project wants a contribution shaped. Every part cites its sources:

- `pull_request_template`: every pull request template at the root, in `.github/` (including `.github/PULL_REQUEST_TEMPLATE/`), and in `docs/`, verbatim or summarized, with its required section headings and checklist items.
- `contributing`: `CONTRIBUTING.md` or `CONTRIBUTING.rst` (root and `.github/`), `docs/contributing*`, `DEVELOPMENT.md`, and the developer documentation they link, with every instruction a contributor must follow. These instructions take precedence over the pipeline's own instructions to the worker and the submission rewrite and review for the content and style of a contribution; no upstream text widens the trusted gates, the scope, or the credentials, or changes where or what is pushed.
- `commit_conventions`: the commit message conventions measured from recent history: the sample, the title length median, 90th percentile, and maximum, the measurable rules (title length limit, literal title prefixes and whether one is required, capitalization, a trailing period, a required body, the body wrap width, a required `Signed-off-by:` trailer, and the most commits a contribution should have), what a machine cannot measure, and typical titles.
- `reviewers`: for every path the contribution may change, the code owners and the people who reviewed or merged recent pull requests there, with links to their reviews and their recurring requests as concrete guidance, including their testing expectations.

A part may be "none found" only with the record of the search: the pull request template search covers the root, `.github/`, and `docs/`; the contributing search covers a root `CONTRIBUTING` file, `.github/CONTRIBUTING`, `docs/` contributing pages, and `DEVELOPMENT.md`. The trusted gate refuses a plan that lacks a part, records a found document it does not cite, records rules that are not measurable, or has no reviewer research for a path in `allowed_paths`. A plan stored before version 2 stays readable; it records no guidelines. A plan of version 2 records no `project`. Both stay readable, and a new plan must be of version 3, which records the contribution guidelines and the project.

The measurable rules are applied by trusted code: the worker gate checks every non-debug commit a worker proposes, and the submission check at `submit-upstream` checks the reviewed series and the reviewed pull request description (see [Integration]({{ '/integration/' | relative_url }})).

The plan's proposal decides `develop` (a bounded patch, with its admission class and allowed paths), `park` (work stops; a human can restart it with `/upstreaming refresh`, optionally with an admission override), or `close`. A `close` is final, so it is only for a project released on PyPI that needs no riscv64 work because the latest release of every requested distribution already installs on riscv64 from PyPI: a riscv64 wheel, or pure-Python wheels only. PyPI is the one registry a close is confirmed from: the trusted gate refuses a close without a PyPI release channel, with a release channel that lacks riscv64, or without a recorded package, and the controller confirms a `close` from PyPI itself, requires each PyPI project to name the upstream repository in its metadata, and rejects one that PyPI does not confirm. A project of another ecosystem that already serves riscv64 is parked with that evidence (see [The plan decides]({{ '/state-machine/engine/' | relative_url }}#the-plan-decides)).

A single `porting-out` artifact must contain a schema-valid plan and proposal bound to task, contribution, revision, tracking-body digest, and complete path coverage. Trusted pre-safe-output validation runs before native Completion. A separate trusted job resolves the exact Claim's verified Result from the gh-aw ledger, downloads only its authorized artifact, revalidates it, publishes a bounded App-authored plan comment, and returns a `porting-publication` artifact for deterministic reconciliation.

If that trusted record job is interrupted after queue Result resolution, its partial `porting-publication` still contains the trusted task, exact Result receipt, plan, and proposal. Ordinary controller collection revalidates all four, requires the original planner run/attempt and authorized artifact identity, reconstructs only the missing deterministic outcome, and retries the idempotent exact-Result comment. It never resets Work, fabricates Result, or reruns the planner.

Dispatcher and planner terminal paths explicitly continue `controller.yml`; workflow completion and the schedule are recovery fallbacks. Missing Work, unavailable queue state, invalid research, malformed artifacts, and exhausted dispatch retries fail closed without fabricating Completion, Result, or state.
